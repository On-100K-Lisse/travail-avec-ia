## 2. Initial diagnosis — Claude (static analysis + patch)

### Discovery: a GPU architecture check

Static analysis of the pristine DLL → it contains an **architecture check** that rejects Turing (0x160), Ampere (0x170), Ada (0x190) and Hopper (0x180), and jumps straight to NGX error code **0xBAD00001** ("NO NR FEATURE MATCHED").

In-game test (RenoDX/ReShade path): RenoDX panel "NO NR FEATURE MATCHED", NGX 0xBAD00001, 0 NR frames, game at 134 fps.

### The "SF" patch

Script `Patch-DLSSNR-310.9.16.ps1` (written by Claude) — binary patch of a **copy**:
- A few bytes modified at the architecture check (exact addresses and instructions deliberately omitted)
- Guards: verifies input/output hashes + original bytes, refuses if source == destination
- SHA-256 of the patched DLL: `ccf6c7b53e95f68e9b03fb91a9a32beba2476980bdecd0475c0f2ffdc7a04af9`
- Note: the patch invalidates the Authenticode signature (normal)

### In-game test of the patched DLL (Dead as Disco)

The arch check is passed (0xBAD00001 → **0xBAD00002**), BUT init then fails on **"Cubin Init failed"** (NGXCG2R::Init) — the 8 CUDA kernels examined were said to be compiled **sm_120 (RTX 50) only**. NR frames: 0, no crash, 131 fps.

**Claude's conclusion:** unusable on Ada via this path — it would take Ada kernels that only NVIDIA can provide. Back to 310.8.

> ⚠️ **Important caveat (see §3):** the patch also zeroed the architecture ID in EDI (`xor edi, edi`). Without examining the later uses of that register, we cannot rule out that it corrupted internal state — the "Cubin Init failed" could be an **artifact of the patch**, not definitive proof. Conclusion downgraded from "proven" to "plausible but unproven".

Afterwards, Claude **refused to continue** (does not bypass a proprietary file). The relay passed to ChatGPT.

## 3. Counter-expertise — ChatGPT (test protocol)

### Critique of the diagnosis

ChatGPT cleanly dismantled the "impossible on Ada":
- Passing the arch check proves we get further into init, **not** that every path requires sm_120 kernels
- Missing evidence: inventory of the kernels *actually loaded*, underlying CUDA error, alternative paths, validity of the internal state after the patch
- **The EDI catch** (see caveat in §2) — a real find

### Test matrix (OptiScaler F5 fork v0.1.32)

| Test | DLL | Preset | Purpose |
|------|-----|--------|---------|
| 00 | 310.8.SF.0 | default | Validate the OptiScaler setup (baseline) |
| 01 | 310.9.16 pristine | A (main model) | Test the main model |
| 02 | 310.9.16 pristine | B (small model) | Isolate the model change |

Protocol: game closed between each test, one variable at a time, logs archived, same scene/resolution/settings, FG disabled. Log: `JOURNAL-TEST.txt`.

### Results (Dead as Disco)

- **Test 00:** 310.8.SF.0 → NR **"Running"**, 6.07 ms GPU, NVIDIA NGX backend, ~68 FPS → setup validated ✅
- **Test 01:** 310.9.16 pristine + preset A → **failure 0xBAD00001** (arch check, not the cubin error)
- **Test 02:** 310.9.16 pristine + preset B → **identical failure 0xBAD00001**

**Verdict:** the architecture check is real and **independent of the preset**. The hypothesis "preset A would work around the problem" is **abandoned**.

### The contradiction that unblocked everything

Testers were reporting 310.9.16 working on Ada (RTX 4060 ~+40%, RTX 4080 SUPER 108→150 fps) — **all via the OptiScaler fork, never via RenoDX**. The explanation was not the preset: it was an **adapted DLL**.

## 4. The ShortFuse lead — openNR repo

### Discovery

- The release notes of **GITC-Uplift v1.3.2** (Oct. 16, 2026, repo `ghostinthecamera/GITC-Uplift`) mention a **310.9.16 "ShortFuse compat-fp16"** build: *"keeps NVIDIA's network weights and adds GPU code for RTX 20, 30, 40 and 50 cards"*, tested on **RTX 4090** (Ada) in DX12 and Vulkan
- Context (press): Uncle Burrito first ported NR to Ada by recompiling 4 of the 15 CUDA binaries; **ShortFuse = clshortfuse, the RenoDX developer**, then extended it to Ampere/Turing with FP16 translation
- **ShortFuse does not distribute the DLL** — he published the open-source toolchain **`clshortfuse/openNR`** (MIT licence) which **rebuilds** the compat-fp16 from the user's pristine DLL

### Build principle

1. Validates the input (pinned hash required — see §6)
2. Extracts the 15 original SM120 fatbins
3. Generates compatibility PTX for **SM75** (Turing), **SM86/SM89** (Ampere)
4. Compiles **45 compatibility cubins**, keeps the original SM120 ones intact
5. Applies the host patches (including the arch-check bypass)
6. **Publishes only if the result matches the reference SHA-256** (reproducible build, self-verified)

### Build performed on the evening of Oct. 19

**Prerequisites installed:** Visual Studio Community 2026 (C++ desktop workload), CMake 4.4.4 (winget, Kitware.CMake package), CUDA Toolkit 13.4.3 (`nvcc` V13.4.92 — exactly the pinned version).

**Blocker encountered and fixed:** the `Visual Studio 17 2022` generator is hardcoded in `build-tools.cmd` and `CMakePresets.json`, but VS 2026 (v18) was installed → CMake error "could not find any instance of Visual Studio".
- **Fix:** replace `Visual Studio 17 2022` → `Visual Studio 18 2026` in both files of the local clone (+ deletion of the `build/` folder soiled by the old generator's cache)
- Justification: the build verifies itself against the reference hash — if the 2026 generator produced a different result, the hash would not match

**Result:**
- `verify-base` → `Verified original DLL: 2BC19BC0…` ✅
- `build.cmd` → extraction, 45 cubins compiled via ptxas 13.4.92, host patches
- Last line: **`Exact reference match: CDFA6C1EC784867182164C7836F324F087B5C9F374D0C9FE46F54999FEABF3ED`** ✅
- The produced DLL is **bit-identical** to ShortFuse's reference build
- File: `build/compat-fp16-310.9.16/nvngx_dlssnr.dll`

- **NR "Running"**, 310.9.16 model created and executed via **NVIDIA NGX**, preset B

### Dead as Disco — RenoDX/ReShade path (1-Click)

- **ACTIVE — NR INJECTED**, **4,856 successful NR frames**, NGX **0x00000001 (ok)**
- Hash = 310.9.16 OpenNR ✅
- ⚠️ The RenoDX panel displayed the label **"310.8.0"** while the hash proved it was the modified DLL → **labels lie, hashes don't**

### Cyberpunk 2077 — NR OK, stability not validated ⚠️

- NR working via RenoDX: ACTIVE — NR INJECTED, **1,187 NR frames**, NGX 0x00000001, preset 2
- **BUT 3 crashes**: GPU hang **0x887A0006** (DXGI_ERROR_DEVICE_HUNG) at the Lighting/FinalFlushBarriers stage every time
- The 26 F6 toggles lead **ruled out** (2nd crash at the same spot with no toggle at all)
- Test: zone passed with NR disabled, NR re-enabled afterwards → **2.5 km at high speed + autopilot ramming tanks, no crash** → the crash depends on a specific situation
- 3rd crash at a **different** spot → the "zone" hypothesis weakens too
- On-100-K-Lisse suspects his Nexus modpack (pre-existing crashes); **we can neither blame the modpack nor clear NR** with the current reports
- **Decisive test postponed** (On-100-K-Lisse fed up for the evening): 15-20 min session, NR disabled from start to finish, same modpack — then ideally modpack disabled + NR active 20 min, stock GPU clocks (a borderline OC + NR load = suspect for a 0x887A0006)

### Crime Scene Cleaner — Feeder mode ✅

- Mode 3 (Feeder) installed via the modified 1-Click folder
- First try: Feeder delivered ~50,000 frames but NR disabled (NeuralUplift=0) → guidance: load a game (not the menu), enable NR, reset the failure latch
- **Result: ACTIVE — NR INJECTED, 5,730 then 17,801 successful NR frames, NGX 0x00000001, preset 2, 2560×1440, ~77-79 FPS**
- Fine diagnosis: depth at zero → fixed by **"Copy depth buffer before clear operations"** (depth 0.013-0.055, 100% finite); motion vectors confirmed in gameplay (61% non-null samples, max 0.21 px), 80,000+ feeder frames
- On-100-K-Lisse's verdict: "everything works perfectly"

## 8. Lessons

- **Labels lie, hashes don't** — the RenoDX panel said "310.8.0", the hash said 310.9.16-compat
- **"This setup fails" ≠ "impossible"** — ChatGPT's rigour reopened a case Claude had closed too quickly
- **A hole in a proof does not necessarily invalidate the conclusion** — Claude was probably right about the sm_120 kernels (ShortFuse had to *add* the 20/30/40 GPU code), but his proof had a hole (the EDI catch)
- **The multi-AI rotation works**: Claude = static diagnosis, ChatGPT = rigour + in-game tests, Kai = research + build + memory. Each brought what the others could not. Demonstrated, not theorized.
- **Never declare something safe on an author's say-so** — the community numbers (4060/4080 SUPER) did not match the static analysis; the truth was a third path (adapted DLL, not a magic preset)
