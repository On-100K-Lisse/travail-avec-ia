## 2. Diagnostic initial — Claude (analyse statique + patch)

### Découverte : contrôle d'architecture GPU

Analyse statique de la DLL pristine → elle contient un **contrôle d'architecture** qui rejette Turing (0x160), Ampere (0x170), Ada (0x190) et Hopper (0x180), et saute directement au code d'erreur NGX **0xBAD00001** (« NO NR FEATURE MATCHED »).

Test en jeu (chemin RenoDX/ReShade) : panneau RenoDX « NO NR FEATURE MATCHED », NGX 0xBAD00001, 0 NR frames, jeu à 134 fps.

### Patch « SF »

Script `Patch-DLSSNR-310.9.16.ps1` (écrit par Claude) — patch binaire d'une **copie** :
- Quelques octets modifiés au niveau du contrôle d'architecture (adresses et instructions exactes volontairement omises)
- Gardes : vérifie hash entrée/sortie + octets d'origine, refuse si source == destination
- SHA-256 de la DLL patchée : `ccf6c7b53e95f68e9b03fb91a9a32beba2476980bdecd0475c0f2ffdc7a04af9`
- Note : le patch invalide la signature Authenticode (normal)

### Test en jeu de la DLL patchée (Dead as Disco)

Le contrôle d'arch est franchi (0xBAD00001 → **0xBAD00002**), MAIS l'init échoue ensuite sur **« Cubin Init failed »** (NGXCG2R::Init) — les 8 kernels CUDA examinés seraient compilés **sm_120 (RTX 50) uniquement**. NR frames : 0, pas de crash, 131 fps.

**Conclusion de Claude :** inutilisable sur Ada via ce chemin — il faudrait des kernels Ada que seul NVIDIA peut fournir. Retour à la 310.8.

> ⚠️ **Réserve importante (voir §3) :** le patch mettait aussi l'ID d'architecture à zéro dans EDI (`xor edi, edi`). Sans examen des utilisations suivantes de ce registre, on ne peut pas exclure que ça ait corrompu l'état interne — le « Cubin Init failed » pourrait être un **artefact du patch**, pas une preuve définitive. Conclusion rétrogradée de « prouvée » à « plausible mais non prouvée ».

Ensuite, Claude a **refusé de continuer** (ne contourne pas un fichier propriétaire). Le relais est passé à ChatGPT.

## 3. Contre-expertise — ChatGPT (protocole de test)

### Critique du diagnostic

ChatGPT a démonté proprement le « impossible sur Ada » :
- Passer le contrôle d'arch prouve qu'on va plus loin dans l'init, **pas** que tous les chemins exigent des kernels sm_120
- Preuves manquantes : inventaire des kernels *réellement chargés*, erreur CUDA sous-jacente, chemins alternatifs, validité de l'état interne après patch
- **Le catch EDI** (voir réserve §2) — vraie trouvaille

### Matrice de test (fork OptiScaler F5 v0.1.32)

| Test | DLL | Preset | But |
|------|-----|--------|-----|
| 00 | 310.8.SF.0 | défaut | Valider le montage OptiScaler (baseline) |
| 01 | 310.9.16 pristine | A (modèle principal) | Tester le modèle principal |
| 02 | 310.9.16 pristine | B (petit modèle) | Isoler le changement de modèle |

Protocole : jeu fermé entre chaque test, une variable à la fois, logs archivés, même scène/résolution/réglages, FG désactivée. Journal : `JOURNAL-TEST.txt`.

### Résultats (Dead as Disco)

- **Test 00 :** 310.8.SF.0 → NR **« Running »**, 6,07 ms GPU, backend NVIDIA NGX, ~68 FPS → montage validé ✅
- **Test 01 :** 310.9.16 pristine + preset A → **échec 0xBAD00001** (contrôle d'arch, pas l'erreur cubin)
- **Test 02 :** 310.9.16 pristine + preset B → **échec identique 0xBAD00001**

**Verdict :** le contrôle d'architecture est réel et **indépendant du preset**. L'hypothèse « le preset A contournerait le problème » est **abandonnée**.

### La contradiction qui a tout débloqué

Des testeurs rapportaient la 310.9.16 fonctionnelle sur Ada (RTX 4060 ~+40%, RTX 4080 SUPER 108→150 fps) — **tous via le fork OptiScaler, jamais via RenoDX**. L'explication n'était pas le preset : c'était une **DLL adaptée**.

## 4. La piste ShortFuse — repo openNR

### Découverte

- Les notes de la release **GITC-Uplift v1.3.2** (16 oct. 2026, repo `ghostinthecamera/GITC-Uplift`) mentionnent une build **310.9.16 « ShortFuse compat-fp16 »** : *« keeps NVIDIA's network weights and adds GPU code for RTX 20, 30, 40 and 50 cards »*, testée sur **RTX 4090** (Ada) en DX12 et Vulkan
- Contexte (presse) : Uncle Burrito a d'abord porté le NR sur Ada en recompilant 4 des 15 binaires CUDA ; **ShortFuse = clshortfuse, le développeur de RenoDX**, a ensuite étendu à Ampere/Turing avec traduction FP16
- **ShortFuse ne distribue pas la DLL** — il a publié le toolchain open-source **`clshortfuse/openNR`** (licence MIT) qui **reconstruit** la compat-fp16 à partir de la DLL pristine de l'utilisateur

### Principe du build

1. Valide l'input (hash pinné requis — voir §6)
2. Extrait les 15 fatbins SM120 originaux
3. Génère du PTX de compatibilité **SM75** (Turing), **SM86/SM89** (Ampere)
4. Compile **45 cubins** de compatibilité, conserve les SM120 originaux intacts
5. Applique les patches host (dont le contournement du contrôle d'arch)
6. **Publie seulement si le résultat matche le SHA-256 de référence** (build reproductible, auto-vérifié)

### Build réalisé le 19 oct. au soir

**Prérequis installés :** Visual Studio Community 2026 (workload C++ desktop), CMake 4.4.4 (winget, paquet Kitware.CMake), CUDA Toolkit 13.4.3 (`nvcc` V13.4.92 — pile la version pinnée).

**Bloqueur rencontré et fixé :** le générateur `Visual Studio 17 2022` est écrit en dur dans `build-tools.cmd` et `CMakePresets.json`, mais VS 2026 (v18) était installé → erreur CMake « could not find any instance of Visual Studio ».
- **Fix :** remplacer `Visual Studio 17 2022` → `Visual Studio 18 2026` dans les deux fichiers du clone local (+ suppression du dossier `build/` souillé par le cache de l'ancien générateur)
- Justification : le build se vérifie lui-même contre le hash de référence — si le générateur 2026 produisait un résultat différent, le hash ne matcherait pas

**Résultat :**
- `verify-base` → `Verified original DLL: 2BC19BC0…` ✅
- `build.cmd` → extraction, 45 cubins compilés via ptxas 13.4.92, patches host
- Dernière ligne : **`Exact reference match: CDFA6C1EC784867182164C7836F324F087B5C9F374D0C9FE46F54999FEABF3ED`** ✅
- La DLL produite est **bit-identique** à la build de référence de ShortFuse
- Fichier : `build/compat-fp16-310.9.16/nvngx_dlssnr.dll`

## 8. Leçons

- **Les labels mentent, les hashs non** — le panneau RenoDX disait « 310.8.0 », le hash disait 310.9.16-compat
- **« Cette config échoue » ≠ « impossible »** — la rigueur de ChatGPT a rouvert un dossier que Claude avait fermé trop vite
- **Un trou dans une preuve n'invalide pas forcément la conclusion** — Claude avait probablement raison sur les kernels sm_120 (ShortFuse a dû *ajouter* le code GPU 20/30/40), mais sa preuve était trouée (catch EDI)
- **La rotation multi-IA fonctionne** : Claude = diagnostic statique, ChatGPT = rigueur + tests en jeu, Kai = recherche + build + mémoire. Chacune a apporté ce que les autres ne pouvaient pas. Démontré, pas théorisé.
- **Ne jamais déclarer sûr sur parole d'un auteur** — les chiffres communautaires (4060/4080 SUPER) ne collaient pas avec l'analyse statique ; la vérité était une troisième voie (DLL adaptée, pas preset magique)
